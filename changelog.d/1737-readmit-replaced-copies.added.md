The control plane re-admits a copy whose storage was replaced and keeps placement off it until then (#1737). Under `joint_fence` a replaced member is a learner: no failover picks it and no majority of a move counts it. When the leader's report shows it caught up under its new storage id, placement writes the same set again at the next generation, naming that id and listing the member in the assignment's `learners`. It counts again once the leader's report at that generation lists it in the new `holds_start` field, the followers holding the generation's start record. Both fields are metadata level 23 under Raft, Postgres migration 0040, and finalizing `joint_fence` needs that level. A leader reports `holds_start`, and a joint fence treats a member kept under another storage id as a set change even with the same node list. The finalize of `joint_fence` stays refused until an end-to-end cluster test shows the sequence.
