The control plane keeps each broker's per-shard Raft root sequence: the heartbeat carries an optional `root` (storage id and last synced sequence), the control plane stores the highest per broker for that storage id at metadata level 33, and `GET /v1/nodes/{node_id}` returns it as `root_sequence`. `felix_replication::raft::open_root` opens a data root through the restore gate with that copy, rotating a root that is behind it and holding one nothing vouches for. Every storage id rotation now starts the root's Raft mark log over. New `felix-broker rotate-storage-id`, run with the broker stopped after restoring a snapshot of its data directory (#2441, #2303). The broker now opens every Raft member through that gate and as a copy of its shard directory (`GroupRuntime::open_copy`), so a directory that may not keep its copy id comes back as a new member; the broker that forms a group asks the others for their copy ids; and a shard directory with a Raft log and no copy file, which only builds from before this wrote, is refused instead of rotated (remove it, or delete and recreate the stream).
