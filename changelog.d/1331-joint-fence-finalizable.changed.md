Brokers now keep a wiped copy from voting under `joint_fence` whenever the fleet has it, with no switch left in the build, and report it as `non_voting`. The control plane no longer refuses `joint_fence` outright: it finalizes it once every serving broker reports `peer_election`, `start_holders` and `non_voting`, so a fleet mixing builds stays safe whatever order they were upgraded in. No release reports `joint_fence` or `peer_election` yet, so a fleet still cannot finalize it. A broker that reports `joint_fence` cannot know whether the fleet has it until its registration is answered, so it treats that window as if the fleet might: until the answer arrives, a copy whose set names another storage id for it answers with a retryable refusal, and a follower takes a fence or records at a new generation only on a fresh control-plane read. A broker that does not report it, which is every release build today, behaves as before. The cluster harness turns joint fences on with `ClusterConfig::joint_fence`, and a new cluster test follows a wiped follower from learner to counted voter across a failover.
