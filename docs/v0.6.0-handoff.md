# v0.6.0 milestone: where things stand

Written 2026-09-20, updated 2026-09-22 after online rebalancing landed. A
point-in-time note, not a living document. Check it against the milestone
before trusting it.

## 2026-09-22: #130 is implemented

Online shard rebalancing is on `main` behind one PR. What it is:

- A shard whose leader is alive is **moved**, never reassigned: the
  destination is staged as a replica, caught up, the leader is fenced (the
  assignment goes `draining`, and a broker never serves a draining
  assignment), the leader reports its log has stopped growing, and only then
  is the destination named leader. Each step is an assignment write, so any
  control-plane instance resumes a move from the store.
- Two triggers: a drained node hands off everything it leads and is reseated
  as a follower; a live node over its share of leadership gives shards to
  one under it. Only over-to-under moves, with in-flight moves counted as
  done, so it converges. `FELIX_SHARD_MOVES_MAX_CONCURRENT` (default 1).
- Five real-process tests in `crates/testing/felix-cluster/tests/routing/rebalance.rs`:
  drain, join, publishes throughout a move, a destination dying
  mid-transfer, and a drain and a join at once. The harness gained
  `add_node`, `drain_node`, `undrain_node`, `drain_until_empty` and
  `shard_successors`.
- Docs: `docs/control-plane.md` (Moving a shard),
  `docs/replication-design.md` (Planned handoff), and a new docs-site page,
  Adding, draining and removing brokers, which is the add/drain/remove half
  of #133.

What it deliberately does not do, each a candidate follow-up rather than a
gap in the mechanism:

- **Publishes are refused for a few sync intervals** between the fence and
  the new owner opening. Closing that needs the successor to open the shard
  before the cut-over is written, which needs a "ready to lead" signal from
  the broker that does not exist yet (nothing reports `active` either).
- **Subscriptions on the old leader are ended, not migrated.** A client with
  a seed list reconnects and is routed to the new owner.
- **No bandwidth limit on the copy.** Only concurrency is bounded. The
  rebuild policy's `bytes_per_sec` could be applied to staged successors the
  same way it paces rebuilds.

#133 is now unblocked for its add/drain/remove half and still blocked on
#131/#132 for topology, install and volume replacement.

## Recommended next: #130, online shard rebalancing

If you're handing the next chunk of work to a dedicated session and want
something substantial rather than another bug-shaped fix, this is it. Reasons,
checked rather than assumed:

- **Actually unblocked.** Its three stated dependencies, #99 (deterministic
  placement), #111 (fenced leadership/failover) and #114 (follower bootstrap),
  are all closed. Confirmed against the tracker, not inferred from the issue
  text.
- **No cloud dependency.** Unlike #425/#557/#597, it's testable against the
  local `felix-cluster` harness. `Cluster::kill_node`, `stop_node`,
  `partition_node`, `pause_node`/`resume_node`, and `place_shards` already
  exist and are the primitives a rebalancing test suite needs for the
  failure-injection half of the work.
- **It's the largest genuine feature gap left.** Everything else open is
  either a tracking issue, needs a decision only a person can make before code
  makes sense, or needs hardware nobody's session has. This is the one place
  where a long run produces a mergeable result without stalling on either.

**Why it clears the "genuinely complex" bar**, and not just by size: the
scope isn't "wire up existing pieces". It needs a *new* fencing mechanism:
an assignment generation/epoch for safe leadership transfer during a planned
move, distinct from the failover fencing #111 already built for an *unplanned*
loss. It also needs a catch-up gate that must never cut over before the destination
durably qualifies, anti-churn policy so placement doesn't oscillate, and two
operationally distinct workflows (operator drain vs. unplanned loss) sharing
one mechanism underneath. The acceptance criteria include concurrent placement
changes and destination-crash-mid-transfer as required test cases, not
stretch goals. That's protocol design, not integration glue.

**One concrete gap found by checking, not guessing:** the harness has no way
to add a new broker to an already-running cluster. `ClusterConfig` fixes node
count at `Cluster::start`, and every existing mutation
(`kill_node`/`stop_node`/`pause_node`/`partition_node`) acts on a broker
already in the set. The "join" workflow in #130's scope (add the destination
as a replica and catch it up) has no harness support today. Expect this to
be part of the work, not a blocker discovered mid-task: budget time for it
before the rebalancing logic itself.

**Before writing code:** verify #130's premises against current placement,
leadership and catch-up code. Three issues closed this session (#527, #536,
#532) turned out to have assumptions that predated other fixes; #130 is older
than most of what shipped this week, so the same check applies here first.

**#133** (the multi-node runbook) depends on #130's outcome for its
add/remove/rebalance procedures and shouldn't be started until #130 has a
shape to describe.

## The one thing worth knowing before planning around #558

**#558 is closed, but its throughput claim was never measured.** The mechanism
is tested: sockets bind, the port set is negotiated, clients spread across it,
and both halves fail their test when reverted. Whether that lifts the
per-broker ceiling is unproven. The acceptance criterion was the receive path
falling from ~88% of one core toward ~88/N, and nobody has run it.

No developer machine can answer it either (#597): a single generator process
is capped by one client I/O thread, so every local sweep comes back flat
whatever the change does. It needs Linux and separate generator machines.

When that session happens, two things matter:

- Measure `FELIX_IO_RUNTIME_THREADS` at 0 and at N+2, not just the default.
  On two brokers a pool of 2 measured 1,341 MB/s against 1,896 with the pool
  off. A run that uses the wrong value reports no improvement, and that reads
  as a verdict on the feature.
- Watch for a decline with listener count. Local runs drifted 543 → 485 MB/s
  as listeners rose. That is inside the noise of a rig that could not measure
  anything reliably, but if it reproduces somewhere trustworthy, N endpoints
  have a cost worth knowing.

## Things that cost time this week

- **Three issues had stale premises.** #527's defect was fixed a week before
  it was filed, #536 said the client computes `shard_for` when it could not,
  and #532's "no timeout scaling anywhere" was already false. Read the code
  before implementing an issue in this backlog; this applies to #130 too.
- **`raft_chaos` and
  `consumer_groups::a_group_position_survives_a_leader_failover` fail under CI
  load and pass alone.** That is five tests now in the same shape: a fixed
  wall-clock budget on a setup wait. Worth fixing as a class.
- **Adding a dependency to `controlplane` changes the demo lockfiles**,
  because the demos depend on it by path and sit outside the workspace. CI
  fails on it. `task lock:refresh` is the fix, and it belongs in the release
  bump.
- **#601 was closed without the underlying gap being fixed.** Its readiness
  guard (`last_log == 0`) is still the only defense against a caught-up-looking
  member with an empty store; #603 only stopped that state from lying about a
  token's validity. If it resurfaces as a different symptom, the design
  decision in the original #601 writeup is still unmade.
